# 使用说明书

## 1. 技能定位

本技能是面向游戏需求分析、测试设计、测试资产导出与源码白盒审计的一体化 QA/SDET 流水线。它用于处理以下输入：

- 文字需求、策划案、系统规则说明。
- UI 原型图、流程图、状态机图、截图、视觉交互说明。
- 配置表、数值表、概率/权重表、字段设计表。
- 项目历史坑点、项目专属术语、风险规则库。
- 源码片段、本地代码文件、代码文件夹、压缩包、后端工程。

核心目标不是只生成测试用例，而是完成“需求解析 -> 风险反问 -> 逻辑建模 -> RTM 追踪 -> 用例设计 -> 自动化导出 -> 源码逆向审计”的闭环。

## 2. 功能结构总览

```text
SKILL.md
├─ Phase 0: 复杂度评估、模块化建议、项目知识加载
├─ Phase 1: 图文表对齐、风险质疑、反问清单
├─ Phase 2: 逻辑全景建模、数据流转图、R/T 追踪编号
├─ Phase 3: 全维度测试设计、DDT、红蓝对抗、P0 自动化伪代码
├─ Phase 4: 结构化载荷校验、Excel/XMind/RTM/JSON 导出
└─ Phase 5: 后端工程 + 配置表联合白盒审计、业务释义注释、攻防测试规划
```

## 3. 阶段使用方式

### Phase 0: 复杂度评估与模块化建议

触发条件：用户提供需求文档、截图、表格、配置或系统说明后立即执行。

输出内容：

- 全文宏观概述。
- 模块划分建议，例如系统功能、UI 表现、表格配置、数值逻辑、网络同步、后台配置、风控安全。
- 项目专属知识库命中项与前置黑盒风险探针。

门禁：必须等待用户确认模块划分，通常回复“确认”后才能进入 Phase 1。

### Phase 1: 图文表深度对齐与质疑

触发条件：Phase 0 的模块划分已确认。

输出内容：

- 文字、图片、表格三方交叉验证结果。
- UI 图中的按钮层级、状态、入口、反馈、适配风险。
- 表格字段名、字段类型、必填项、默认值、边界值、非法值、字段间约束。
- 文档、图片、表格之间的矛盾点与缺失异常流。
- 《多模态反问清单》或《模块专项反问清单》。

门禁：必须等待用户回复“理解一致”后才能进入 Phase 2。

### Phase 2: 动态全景建模

触发条件：Phase 1 的疑问已完成对齐。

输出内容：

- Markdown 树状逻辑图。
- 主流程、异常流、回滚流、恢复流、状态转移。
- 前置条件、后置条件、资源约束、数值约束。
- 数据流转图，说明配置表如何驱动游戏内功能表现。
- 需求编号 `R1/R2/R3...` 与表格字段编号 `T1/T2/T3...`。

### Phase 3: 全维度测试设计

触发条件：Phase 2 已完成逻辑建模。

输出内容：

- 高覆盖率测试用例，字段包括 ID、模块、子功能、标题、优先级、前置条件、步骤、预期结果、需求映射。
- 功能、UI、弱网、断线重连、多端并发、资源原子性、数值溢出、防刷安全覆盖。
- 数据驱动测试用例，覆盖空值、非法值、重复项、精度丢失、权重/概率算法、最大值/最小值/默认值。
- 红蓝对抗测试补强：守方证明、攻方破坏路径、逻辑绕过、非法刷取。
- P0 核心路径的 Python 或 Airtest 自动化伪代码。

约束：每条用例至少映射一个 `R` 或 `T` 编号。

### Phase 4: 自动化工具链导出

触发条件：当前模块或全部模块的用例与 RTM 已生成。

输出内容：

- 《测试用例表》。
- 《需求跟踪矩阵》。
- XMind Markdown 级联结构。
- 结构化 JSON 载荷。
- `.xlsx` 测试资产文件，包含多页签、表头样式、筛选、冻结窗格、自动列宽。

优先使用脚本：

```powershell
python C:\Users\yangfeng\.codex\skills\game-qa-pipeline-data-vision-expert\scripts\validate_game_qa_payload.py --input-json <payload.json>
python C:\Users\yangfeng\.codex\skills\game-qa-pipeline-data-vision-expert\scripts\build_game_qa_data_vision_workbook.py --input-json <payload.json> --out <asset.xlsx>
```

### Phase 5: 后端工程 + 配置表联合逆向审计

触发条件：Phase 0-4 已完成需求理解、RTM 建模和用例设计后，需要对白盒实现和配置驱动做闭环验证。默认审计后端工程 `C:\NuoYaIdle\Server\`，并默认读取配置表目录 `C:\NuoYaIdle\Tools\表格配置及转换\excel\`，不要求用户贴相关代码；用户提供的源码片段、本地路径、文件夹或压缩包只作为补充输入。

执行规则：

- 从已确认的 `R/T`、需求关键词、系统名、玩法名、配置字段出发，自动定位配置表/Sheet/字段/值、协议入口、Handler/Controller、Service/Manager/Domain、配置读取、DB/Cache、事件、回包和异常恢复链路。
- 若默认工程根不存在或不可读，只询问新的后端工程路径，不要求用户贴代码。
- 若默认配置表根不存在或不可读，只询问新的配置表目录，不把配置缺失静默解释为代码缺陷。
- 默认只读审计，不启动服务、不执行迁移、不写数据库、不跑破坏性命令。
- Step 0 到 Step 4 必须逐步输出、逐步停顿、逐步等待用户确认。
- 先做需求范围隔离和 RTM 映射，再做源码拓扑、调用链、状态链、资源链审计。
- Step 0 必须输出代码与配置追踪矩阵：`需求ID -> 表字段ID -> 配置表路径 -> Sheet -> 配置字段 -> 配置值 -> 默认值 -> 边界值 -> 配置风险 -> 协议/入口 -> 业务承载 -> 数据承载 -> 输出承载 -> 风险点 -> 测试用例ID -> 命中置信度`。
- Step 2 默认为只读业务释义；只有用户明确要求“落地注释”时才允许新增 `[新增业务释义注释]`，不得修改任何已有源码行，不得新增调试日志、桩代码或可执行观测代码。
- 最终输出源码业务释义、调试观察策略、守方证明、攻方破坏路径、白盒审视结论单。

## 5. 常见使用场景

### 场景 A: 只分析需求文档

用户可以说：

```text
使用这个技能分析这份游戏系统需求，先做模块划分和反问。
```

技能会从 Phase 0 开始，不会直接跳到用例生成。

### 场景 B: 文档包含图片和表格

用户可以上传或粘贴文字、截图、表格内容，并说明：

```text
这是文字 + UI 图 + 配置表，请按图文表三位一体流程分析。
```

技能会重点检查文字、图片、表格之间的矛盾和缺失异常流。

### 场景 C: 需要最终 Excel 资产

用户可以在 Phase 3 后说：

```text
进入 Phase 4，生成 Excel、RTM 和 XMind。
```

技能会先进行结构化载荷校验，再用 Python 脚本生成 `.xlsx` 文件。

### 场景 D: 需要后端工程 + 配置表白盒闭环审计

用户可以在需求分析和用例设计完成后说：

```text
进入 Phase 5，基于 C:\NuoYaIdle\Server\ 和 C:\NuoYaIdle\Tools\表格配置及转换\excel\ 自动定位本期需求涉及的后端代码、配置字段和值，并做联合白盒审计。
```

技能会按 Step 0-4 逐步审计，默认只读，不会要求用户贴代码，也不会直接修改业务代码或配置表。

### 场景 E: 更新项目专属知识库

用户可以说：

```text
把这次发现的避坑点加入项目知识库。
```

技能会使用 `project-memory-template.md` 的格式沉淀术语、坑点、风险规则和证据来源。

## 6. 输入与配套技能建议

- 如果输入是 `.docx`，先用 `docx` 技能提取正文、表格和图片信息，再进入本技能。
- 如果输入是 `.pdf`，先用 `pdf` 技能提取文本、表格、图片或 OCR 内容，再进入本技能。
- 如果主要交付物是 `.xlsx/.csv/.tsv`，或需要清洗表格文件，配合 `xlsx` 技能处理。
- 如果已完成需求分析并需要白盒闭环，本技能默认使用 `C:\NuoYaIdle\Server\` 和 `C:\NuoYaIdle\Tools\表格配置及转换\excel\` 进入 Phase 5；本地源码路径、文件夹或压缩包可作为补充输入。

## 7. 标准交付物

建议最终文件命名：

- `系统名_总设计文档.md`
- `系统名_XMind导图.md`
- `系统名_结构化载荷.json`
- `系统名_测试资产.xlsx`

Excel 至少包含：

- `测试用例库`
- `需求跟踪矩阵`

根据任务复杂度可增加：

- `字段校验矩阵`
- `风险清单`
- `白盒审计结论`
- `代码与配置追踪矩阵`
- `配置表证据摘要`
- `自动化候选集`

## 8. 不会做的事

- 不会跳过 Phase 0 的模块化确认。
- 不会跳过 Phase 1 的“理解一致”门禁。
- 不会忽略图片、表格或源码证据。
- 不会生成没有 `R/T` 映射的测试用例。
- 不会把未校验的结构化载荷直接导出为正式 Excel。
- 不会要求用户贴代码才能进行 Phase 5；默认从 `C:\NuoYaIdle\Server\` 检索需求承载代码。
- 不会忽略固定配置表目录；默认从 `C:\NuoYaIdle\Tools\表格配置及转换\excel\` 读取相关字段和值参与判断。
- 不会在 Phase 5 默认写入源码；Step 2 只有用户明确要求“落地注释”时才新增业务释义注释。
- 不会修改、保存或覆盖原始配置表。
- 不会在 Phase 5 Step 2 修改已有源码行。
- 不会把用户未确认的推断当成事实。

## 9. 多遍自检规则

任务完成前必须至少检查：

- Phase 0-5 结构是否仍然完整。
- 图文表三位一体、RTM、DDT、红蓝对抗、Excel/XMind/JSON、源码白盒能力是否未丢失。
- 每条测试用例是否映射 `R` 或 `T`。
- 表格字段是否覆盖最小值、最大值、默认值、空值、非法值、重复项、精度和权重。
- Excel 前是否通过结构化载荷校验。
- Phase 5 是否已输出代码与配置追踪矩阵，并标记高 / 中高 / 低命中置信度。
- Phase 5 是否已读取相关配置表字段和值，并区分代码缺陷、配置缺陷、代码配置不一致、配置证据不足。
- Phase 5 是否保持只读审计优先，未在无明确授权时写入源码。
- 结尾是否追加本次规则增量，并询问是否有新避坑点需要加入资产库。
