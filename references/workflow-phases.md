# Phase 0-4 流程规则

## Phase 0: 需求分块与知识加载

严格先做全局扫描，再进入模块级分析。

必须输出：

| 输出项 | 要求 |
|---|---|
| 全文宏观概述 | 覆盖正文、UI 图、表格、配置表和源码输入迹象 |
| 模块划分建议 | 基于文档长度、系统数量、规则耦合度、配置表复杂度和恢复链路复杂度 |
| 风险探针包 | 明确本轮挂载哪些探针，例如原子性、状态机、保底算法、交易限制、恢复链路、概率权重、背包满补偿 |
| 项目记忆匹配 | 自动匹配项目术语、历史坑点、能力边界 |

常见模块划分：

- 系统功能
- 数值与配置表
- UI 表现
- 协议与后端校验
- 恢复链路
- 资产流转
- 跨服同步

确认门禁：输出模块划分建议和探针包后，必须等待用户回复“确认”。

## Phase 1: 三位一体审计与坑点扫描

强制核对文字描述、UI 原型图、配置表数值、用户确认和可用源码。不得只截取某段正文或某张 UI 图就定性完整规则。

必须执行：

- 交叉验证：核对文字描述、UI 原型图、配置表数值。
- 风险探测：检索历史坑点，识别曾经出过 Bug 的逻辑场景。
- 全文规则合并：对同一对象的全部描述做上下文归并，例如“材料”“显示装备”“背包内”“选择材料”“自动添加”“提交校验”。
- 表格结构解析：识别字段名、数据类型、取值范围、默认值、必填项、唯一性、字段间逻辑关联、公式或权重依赖。
- 数据一致性校验：核对概率/权重总和、阈值、默认值、最小值、最大值、空值、重复项、孤儿引用。

### 需求规则承载域识别

凡是同一对象在正文、UI 图、表格、用户确认或代码中有不同描述，必须先识别规则承载域，再决定是否构成冲突。不得把“正文某处未提到”直接等同于“不允许存在该限制”。

| 承载域 | 含义 | 审计处理 |
|---|---|---|
| 前端展示规则 | UI 列表显示、排序、筛选、按钮状态、提示文案 | 不得默认只是视觉规则；若它决定玩家可选择对象，必须纳入候选集规则 |
| 自动添加规则 | 一键添加、默认选择、优先级选择 | 只约束自动行为，不一定约束手动提交 |
| 手动选择规则 | 玩家可从背包/列表中选择哪些对象 | 需要判断是否要求服务端同步校验，防止绕过前端 |
| 服务端准入规则 | 服务端最终是否接受请求 | 可直接作为强校验依据 |
| 旧系统继承规则 | 旧功能已有逻辑，本期只回归 | 不得误判为新增需求，除非与本期状态互相影响 |
| 展示/对比口径 | 仅影响结果界面展示和比较 | 不得扩展成数值或服务端规则，除非文档明确说明 |

### 全文证据合并门禁

输出缺陷或反问前必须执行一次反证检索：

1. 检索同一对象在全文中的所有描述。
2. 将每条规则标注来源：正文、UI 图、表格、用户确认、代码实现。
3. 判断这些规则是互补、冲突、层级不同，还是表述不完整。
4. 如果代码行为能被文档任一位置合理解释，不得直接输出为确定性缺陷；必须改为“需求歧义/需确认”。
5. 只有当用户明确确认该规则不适用，或全文没有任何支持证据时，才允许定性为代码缺陷。

输出《深度反问清单》必须使用：

| ID | 模块 | 位置 | 类型 | 观察 | 风险 | 反问 |
|----|------|------|------|------|------|------|

反问覆盖面至少包括：

- 图像交互不确定性
- 数值边界与极值
- 默认值、空值、封顶与重置
- 非法输入与异常流
- 恢复链路与状态机闭环
- 历史坑点复现风险
- 同一对象在展示、自动添加、手动选择、服务端提交四层中的规则差异

确认门禁：只有用户回复“理解一致”后方可继续。

## Phase 2: 逻辑全景建模与 RTM

输出不限字数的 Markdown 树状逻辑图。

必须包含：

- 主流程
- 异常流
- 回滚流
- 恢复流
- 数据流转图
- 图文表闭环
- 配置表如何驱动游戏行为
- `断线重连（Reconnect）`
- `位面切换`
- `R` 需求编号
- `T` 表格字段编号

逻辑树至少包含以下节点，且 `当前模块` 与 `功能点` 必须使用系统名前缀命名：

```markdown
- 系统名-当前模块
  - 系统名-功能点
    - 需求 ID
      - R1 ...
    - 表字段 ID
      - T1 ...
    - 前置条件
    - 主流程
    - 异常流
    - 数据流转图
    - 图文表闭环
    - 后置结果
```

## Phase 3: 资深设计与红蓝对抗

必须使用等价类、边界值、错误推测、状态转移、因果关系和风险猜测生成高覆盖用例。

测试设计必须满足：

- 每个功能点至少两条反向测试路径。
- 每条用例至少带一个 `R` 或 `T` 追踪标签。
- 高风险链路强制包含并发、断线、恢复、资源一致性测试。
- P0 路径输出 Python / Airtest 自动化脚本伪代码。

红蓝对抗优先火力点：

- 多层 Buff 叠加后的数值溢出、负数、重复乘算或异常截断。
- 并发请求、重复提交、断线恢复下的事务一致性与原子性。
- 非法/越权/极值/负数请求参数。
- 旧状态重放、伪造协议、RPC 脏数据拦截与篡改。
- 背包满、邮件补偿、资产出口拦截、跨服传输丢失。

用例表必须使用以下列，且 `模块` 与 `子功能` 两列必须使用系统名前缀命名：

| ID | 模块 | 子功能 | 标题 | 优先级(P0-P3) | 追踪编号 | 前置条件 | 步骤 | 预期结果 |
|----|------|--------|------|---------------|----------|----------|------|----------|

## Phase 4: 全自动化资产交付

必须执行数据健康检查：

- 清洗字段首尾空格。
- 清理非法换行和公式残留。
- 校验 ID 唯一。
- 校验优先级符合 `P0` / `P1` / `P2` / `P3` 或 `P0(...)` 格式。
- 校验每条用例至少关联一个 `R` 或 `T`。
- 校验 RTM 覆盖测试用例中的全部追踪编号。
- 校验模块、子功能、标题、XMind 节点是否统一携带系统名前缀。

交付资产：

- `系统名_总设计文档.md`
- `系统名_XMind导图.md`
- `系统名_结构化载荷.json`
- `系统名_测试资产.xlsx`

详细输出契约见 `output-contracts.md`。
