# Phase 5: 后端工程 + 配置表联合逆向审计与动态渗透策略

Phase 5 在 Phase 0-4 完成需求理解、RTM 建模和用例设计后，或在 Phase 4R 完成增量复审并形成最新基线资产后按需触发，用于建立“需求 -> 配置 -> 源码 -> 风险 -> 测试”的闭环证据链。不再要求用户贴相关代码；默认以后端工程根目录 `C:\NuoYaIdle\Server\` 作为源码搜索根，并以配置表根目录 `C:\NuoYaIdle\Tools\表格配置及转换\excel\` 作为配置证据根，自动按需求链路定位承载代码、配置字段和值。

用户提供的聊天代码片段、本地文件路径、文件夹或代码压缩包仍然有效，但只作为补充输入一并审计。若默认工程根不存在、不可读或明显不是后端工程，只询问新的后端工程路径，不要求用户贴代码。

若默认配置表根不存在、不可读或不包含可识别表格文件，必须标记“配置证据不足”，并只询问新的配置表目录；不得把配置缺失静默解释为代码缺陷。

Phase 5 默认只读审计。只有当用户明确要求“落地注释”或“进入 Step 2 写入注释”时，才允许在 Step 2 对已确认范围新增业务释义注释。

Phase 5 的 `0/1/2/3/4` 每一步都必须独立输出、独立停顿、等待用户确认后才能进入下一步。不得在每步结尾追加泛化建议提醒或重复性总结。

Phase 5 Step 0 开始前必须先读取 `references/project-memory-template.md`，用于建立当前项目的技术栈、协议入口、存储层、缓存层、工程模块和能力边界认知。该项目记忆只作为审计辅助，不能覆盖当前需求文档、配置表证据、源码证据或用户在当前会话中的确认结论。

若当前会话同时出现新版策划文档/变更说明与源码更新请求，必须先完成 Phase 4R，锁定最新需求基线、受影响 `R`/`T`、用例和配置范围后，才能进入本阶段；不得跳过 Phase 4R 直接对白盒审计范围下结论。

## 修复后 Diff 复审触发点

当用户表示“源码已更新”“开发已修 bug”“重新审一下 diff”“基于上一轮理解复审”“重新输出白盒审视结论单”等含义时，触发 Phase 5 的独立复审模式。

复审模式的目标不是重新跑完整 Phase 0-4，也不是追加 Step 4 后续流程，而是基于上一轮已确认的需求理解、RTM、代码与配置追踪矩阵、白盒发现和项目规则记忆，对本地源码变更差异进行针对性代码审核，并重新输出《白盒审视结论单》。

复审模式执行规则：

- 优先读取上一轮 Step 0 已确认代码审计范围内的 Git 工作区差异，使用 `git status`、`git diff --stat`、`git diff -- <已确认文件或目录>` 等只读命令定位变更文件、变更方法和变更行。
- 若当前目录不是 Git 仓库或无法取得 diff，必须说明 diff 证据不足，并改为按用户提供的变更文件、变更说明或文件时间差进行低置信复审；不得编造 diff。
- 复用上一轮需求理解和 findings，不重新向用户索要需求文档，不重新跑完整需求拆解，除非 diff 触及新系统、新配置表、当前会话已进入或应进入 Phase 4R，或用户明确说明需求变更。
- 复审 diff 范围必须限定在上一轮 Step 0 已确认的代码审计范围内；超出已确认范围的工作区变更只记录为“范围外变更”，不得纳入缺陷定性、复测点或白盒结论。
- 审计范围只覆盖已确认范围内的 diff 行、diff 所在方法、直接上下游调用、受影响配置读取点、状态字段、资源扣除/发放点、回包/事件/存库点和异常恢复路径。
- 若上一轮之后已完成 Phase 4R，复审时必须以最新确认的 `RTM`、测试资产、结构化载荷和《策划变更影响矩阵》为基线；不得继续沿用被新版策划文档判定为已变更、已废弃或已失效的旧需求范围。
- 对上一轮每个 finding 必须给出状态：`已修复`、`部分修复`、`未修复`、`无法判断`、`不受本次 diff 影响`。
- 必须识别修复引入的新风险，例如只修客户端不修服务端、只修普通路径不修旁路路径、修复后破坏原有成功路径、重复拦截导致正常请求失败、空判断位置错误、幂等返回码不一致、事务补偿只覆盖部分材料。
- 若 diff 涉及配置读取、材料筛选、权重、祝福值、次数重置、未保存态出口、保存选择、登录恢复或资源扣除，必须同步复查对应配置字段和上下游口径。
- 复审模式默认只读，不允许落地注释、插桩、格式化或修改源码。

复审模式输出结构必须包含：

1. 《Diff 变更摘要》：变更文件、方法、行号范围、变更类型、命中上一轮需求/风险点。
2. 《Finding 修复状态矩阵》：上一轮 finding、对应 diff 证据、当前状态、剩余风险。
3. 《新增/回归风险》：仅列 diff 引入或暴露的新风险；无则写“未发现新增明文级风险”。
4. 《必要复测点》：只列与 diff 直接相关的守方证明和攻方破坏测试。
5. 《白盒审视结论单》：最终评级、发现缺陷、盲区警告、复测重点、需要继续追踪的下游。

复审模式门禁：

- 若 diff 范围小且上一轮白盒上下文完整，可直接输出完整复审结果和《白盒审视结论单》。
- 若 diff 范围过大、跨多个系统、上一轮上下文缺失或无法确定本次修复目标，先输出《Diff 变更摘要》和推荐复审范围，等待用户确认后再继续。
- 复审模式结束后即结束本轮 Phase 5，不得追加测试执行清单、缺陷单模板或新的审计范围建议，除非用户明确要求。

- `.zip`、`.rar`、`.7z`、`.tar`、`.tar.gz` 等压缩包

- 若表格存在多行表头、说明行、隐藏列或合并单元格，必须在输出中说明识别依据和置信度。

必须输出：

- 源码形态识别
- 工程可用性检查结果
- 配置表可用性检查结果
- 《配置表证据摘要》
- 《核心源码拓扑树》

- RTM 匹配范围
- 代码与配置追踪矩阵
- 命中置信度分级
- 合并推荐审计范围

拓扑树不得只列入口方法，必须尽量展开与入口直接或间接相关的调用链方法，包含文件路径、类名、方法名、行号、协议入口、存库点、异步回调、配置读取点、高风险状态流转点和调用关系。

调用链源码图示例：


闭环证据链优先追踪：

```text
协议入口 -> 业务校验 -> 资源/状态变更 -> 存库/缓存 -> 回包/事件 -> 异常/恢复
```

智能范围合并：

- 严禁一次性深度读取无关全工程。

- 推荐依据必须说明需求 ID、方法名、行号范围、上下游闭环追踪点和推荐理由。

命中置信度规则：

- 低置信命中必须标记为“需确认”，不得直接输出确定性缺陷。

Step 0 门禁：输出工程可用性、配置表可用性、源码形态、配置表证据摘要、拓扑树、RTM 匹配范围、代码与配置追踪矩阵和合并推荐审计范围后，询问用户是否确认按该范围进入 Step 1。

## Step 1: 需求溯源、边界隔离与漏洞扫描

必须执行：

- 逆向寻踪：明确代码实现了哪些 `R` 和 `T`。
- 代码配置追踪矩阵校验：逐项核对代码与配置追踪矩阵是否能从配置表字段和值闭合到代码读取点、业务承载、数据承载、输出承载和异常恢复。
- 配置承载审计：若代码读取了某配置字段，但表格不存在、字段不存在、值为空或类型不匹配，优先标记为 `配置承载缺失风险`。
- 代码配置脱节审计：若配置表存在字段和值，但代码没有读取、读取字段名不一致或忽略关键值，标记为 `代码配置脱节风险`。
- 配置值风险审计：识别数值越界、概率不闭合、权重异常、重复 ID、非法字符、默认值危险、开关误配、时间窗口异常。
- 需求边界隔离：识别与本期需求无关的历史遗留逻辑或旁路系统代码，标记为 `[非本期需求 (Out of Scope)]`。
- 审计过滤：对 `[非本期需求]` 代码段跳过白盒漏洞扫描、并发审查与测试建议生成，除非存在直接副作用风险。
- 上下游自查：对每个高风险结论给出上游入口、当前方法、下游落地点、异常/回滚路径和协议/事件输出。
- 全文规则反证检索：发现额外限制、额外校验或额外筛选时，回查同一对象的全部规则来源。
- 材料/候选集四层审计：候选展示、自动添加、手动选择、服务端提交。

缺陷定性必须选择：

- `确定缺陷`
- `配置缺陷`
- `代码配置不一致`
- `配置承载缺失风险`
- `代码配置脱节风险`
- `需求歧义`
- `需追踪下游`
- `合理防绕过`
- `[非本期需求 (Out of Scope)]`

只有代码或配置与已确认强规则直接冲突，且全文、配置表和代码链路没有其他规则可解释时，才能写成确定缺陷。若 UI 候选集存在同类限制，服务端同步限制默认先视为可能的防绕过校验。

配置证据优先级：

- 配置表字段和值可以解释代码分支时，不得直接把代码分支判为缺陷。
- 配置表字段和值与代码读取逻辑冲突时，优先定性为 `代码配置不一致`，再判断影响范围。
- 配置缺失不能自动等价于代码缺陷；必须说明是配置未找到、字段未找到、值为空、类型不符还是读取链路未定位。
- 代码正确但配置值危险时，输出 `配置缺陷` 或 `配置值风险`，并转化为 DDT 和攻防测试。

Finding 标题降级规则：当代码行为与某处规则冲突，但全文另一处存在可能支持代码的规则时，标题必须写成 `[需确认] XXX 规则存在正文口径与前端显示/候选集口径差异`。

Step 1 输出必须包含《需求溯源、边界隔离与漏洞扫描总结》，汇总已覆盖需求、非本期范围、确定性缺陷、需求歧义、风险盲区和当前证据强度。

Step 1 门禁：询问用户是否确认进入 Step 2。

## Step 2: 源码业务释义注释

本步骤默认为只读输出源码业务释义，不写入工程。只有用户明确要求“落地注释”或“写入业务释义注释”后，才允许新增业务释义注释。

严禁：

- 修改任何已有源码行。
- 删除、移动、重排、格式化旧代码。
- 改变量名、方法签名、import、缩进或换行。
- 新增 `[QA Debug]` 日志。
- 新增 `[新增插桩代码]`。
- 新增可执行观测代码。

若用户未明确要求写入，必须输出《源码业务释义说明》并保持只读，不得调用编辑工具修改工程文件。

若用户明确要求写入，且 Step 0/1 已确认本地可写源码文件、文件夹或压缩包范围，进入 Step 2 后必须只在已确认范围内新增中文业务释义注释，并用语言原生注释标明 `[新增业务释义注释]`，例如 Java：

```java
// [新增业务释义注释][QA Review] 这里说明业务目的、状态变化、资源/数据库/缓存/协议影响和失败风险。
```

注释深度要求：

- 说明业务目的。
- 说明状态变化。
- 说明输入依赖。
- 说明资源、缓存、数据库或协议回包影响。
- 说明失败会造成什么风险。

注释覆盖率：

- Step 0/1 已确认审视范围内，有效业务代码行新增业务释义注释覆盖率不得低于 80%。
- 有效业务代码行不包含空行、纯括号行、package/import、注解、已有注释、简单字段声明、机械 getter/setter、纯日志行和 `[非本期需求]` 折叠段。
- 注释可以覆盖连续 1-3 行相关代码，但必须明确说明这些行的共同业务作用。

聊天片段交付：

- 若只有聊天代码片段，输出局部 Patch Diff 或短片段注释后代码。
- 必须明确“未写入本地源码”。

Patch Diff 输出：

- 严禁重写整个超大源文件。
- 必须使用 Git-Style 局部补丁格式，或明确指出“在 XXX 方法第 N 行下方插入以下 N 行注释”。

Step 2 完成后必须输出覆盖率自检，并在必要时运行编译、静态检查或文本检索确认没有新增可执行代码。

Step 2 门禁：询问用户是否确认进入 Step 3；不得再要求用户二次确认注释落地。

## Step 3: 守方与攻方渗透规划

必须直接围绕当前审计代码块输出高密度测试动作。

守方证明必须包括：

- 核心入参组合
- 数据库状态
- 缓存状态
- 内存状态
- 日志关键词
- 协议回包字段
- 配置命中校验点

攻方破坏必须包括：

- 非法参数
- 越权参数
- 极值参数
- 负数参数
- 断线/切场景回调孤儿
- 高频重复提交
- 并发竞态
- RPC 脏数据拦截与篡改
- 旧状态重放
- 伪造协议

每条测试动作必须绑定当前代码位置或下游方法，写清测试目的、前置条件、操作步骤、观测点、通过标准、失败信号。

Step 3 门禁：询问用户是否确认进入 Step 4。

## Step 4: 白盒审视结论单

输出《白盒审视结论单》。

最终评级必须从以下选项中选择一个：

- `通过`
- `需补充用例`
- `存在高危漏洞`
- `需追踪下游`
- `信息不足`

结论单必须包含：

- 最终评级和依据
- 发现缺陷
- 盲区警告
- 守方证明测试数
- 攻方破坏测试数
- 需要补充源码后才能执行的测试数

若无确定缺陷，写“未发现明文级代码错误”。若仍有信息不足，只能写入“盲区警告”。Step 4 完成后即结束本轮 Phase 5，不得追加插桩、断点统计、续审提示或新的审计范围建议。
